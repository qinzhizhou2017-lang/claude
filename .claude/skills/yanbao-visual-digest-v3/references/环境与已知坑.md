## 二、五个必栽的坑

1. **无头浏览器被 Claude Code 沙箱静默掐掉**
   现象：Edge/Chrome 退出码 0、无 stdout、不落图/不落 PDF，脚本报"渲染结果里没有 xxx"。
   根因是沙箱，不是脚本、也不是 `--no-sandbox` 参数。**用 `dangerouslyDisableSandbox` 跑就正常，别去改脚本。**

2. **`--print-to-pdf` 退出码 0 但几十秒后才落盘**
   进程一返回就判文件存在 → 误报 `render FAILED`（其实 PDF 是成功的）。
   修法：轮询等文件大小**连续两次不变**才算完（`render_pdf.py` 已内置，`--wait` 默认 90s）。
   **旧的 render.py（A4 版 / 长图版）没修，还带这个坑**——哪天报 FAILED 先去看文件是不是其实写出来了。

3. **并行渲染互相顶掉 + 残留浏览器进程**
   共用默认 profile 会互顶；跑完一批残留过 23 个 msedge。
   修法：每次渲染用独立临时 profile，结束按 profile 路径精确 kill（只杀自己起的）。`render_pdf.py` 已内置。

4. **cv2.imread 读不了中文路径** → 一律 `np.fromfile + cv2.imdecode`。
   （pyzbar 在 Windows 缺 DLL 跑不起来，二维码解码全部走 cv2。）

5. **二维码缩放**：占位码能扫、真码扫不出 → 先怀疑缩放。
   `image-rendering:crisp-edges` 最近邻缩放会整行丢模块，占位码靠纠错扛过去、真码直接废——**不要加**。
   显示尺寸给 **360px**（320px 处于临界，同码同尺寸一张过一张挂，取决于 JPEG 伪影）。
   THE PORT 真码是**微信个人号加好友码，会过期**，隔一段时间要找用户重新要。

## 三、字体

- Windows 字体名是 `Noto Serif SC` / `Noto Sans SC`，**不是** Linux 的 `Noto Serif CJK SC`——写错就掉字回退。
- macOS 中文正文用 `PingFang SC`；引文/大判断用宋体（`Songti SC` 或思源宋）。
- 拉丁与数字用等宽 + `tabular-nums`。
- 无头 Chrome 的 print-to-pdf **会嵌字体**，所以可以用 Google Fonts；Claude Design 那条链路反而会掉字。

## 四、渲染与验收命令（Mac）

```bash
# HTML → PDF
python3 scripts/render_pdf.py 成品.html 成品.pdf

# 页数 + 留白漏风审计
python3 scripts/verify_pdf.py 成品.pdf --pages 3

# 逐页出 PNG 拼版肉眼复核（本机无 poppler，用 pypdfium2）
python3 - <<'PY'
import pypdfium2 as pdfium
d = pdfium.PdfDocument("成品.pdf")
for i in range(len(d)):
    d[i].render(scale=2.6).to_pil().save(f"页{i+1:02d}.png")
PY
```

## 五、成本与时间的真实口径（别再凭感觉说"太耗 token"）

- 9.01 单次会话（2 篇）：**46 次工具调用 / output 8.6 万 / cache_read 1012 万**（去重口径）。
  8.28（3 篇）：60 次 / 13.1 万 / 1472 万。按篇折算两次同量级（≈4.3–4.4 万 output/篇）。
- **大头不是"手写 HTML"**（只占 output 的 38%），而是：
  ① 每轮渲染-看图-微调都拖着 24–32 万 token 的上下文（估占 58%）
  ② 在大工作区开会话自带 ≈8 万 token 固定前缀（长 CLAUDE.md + 记忆索引 + 几十个 MCP 工具目录，估占 37%）
- **墙钟由工具往返次数线性决定，不是 token 量**：四篇 token 都是 240–380k，耗时 20→138 分钟，往返 30→96 次。
  图片型每页一次 Read 是主因。10 篇并行 vs 串行加速比只有 **3 倍**，不是 10 倍。
- 3 份研报 → 12 页端到端约 25 万 token；5 份预估 45–55 万（超线性，来自溢出校验轮次与上下文累积）。
  **>3 份分两批做**，页码提前规划死，最后 pypdf 合并。
- 可以砍的浪费：强模型通读全文、读母本 HTML 学样式、给有文本层的页读 PNG、重复看拼版图、
  短正文硬凑页数、去找"能读长 PDF 的插件"。

## 六、为什么不能"一次读 100 页"（水池类比，别再问了）

1M 上下文是水池容量，但四道口都比池子小：

| 口 | 口径 | 含义 |
|---|---|---|
| 进水管 | API 直传 PDF 单请求 32MB/600 页，每页文本 1,500–3,000 token；Claude Code 的 Read：PDF 每次 ≤20 页、文本单次 ≤25,000 token | 100 页 ≈15–30 万 token + 100 张图，装得下但至少五次往返 |
| 每轮重灌 | 每次工具往返都重发整段上下文，缓存只降价不降体量 | 46 轮 × 24 万 = 1012 万 |
| 注意力 | 长上下文中段利用弱于首尾 | "塞进去" ≠ "选出来" |
| 出水口 | 最大输出 128K；成品 3 页 ≈2,500 字，与输入多少无关 | 读得多不等于写得全 |

**没有"一劳永逸的插件"**：NotebookLM / ChatPDF / RAG / MinerU / Docling 内部都是切块→抽取→合并。
RAG 更是错路子——它要先知道问什么，而"全篇选最值得的 8 条"是全局排名（map-reduce），不是检索。
**这套 skill 本身就是那个插件**，前提是它真的被加载（所以才要装到用户级）。
